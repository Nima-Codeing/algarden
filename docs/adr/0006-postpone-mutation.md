# 0006. 突然変異を v1 から外し、v1.1 に回す

- 状態：採用
- 決定日：2026-07-28

## 背景

Tendril Algorithm では、ノード図形集合群（ノードが集まりながら綺麗な図形になっている部分）を「変異」として、成長の途中で一定の確率で生むことにしていた。変異は低い確率で起き、新しいノードに「設計図」として宿る。設計図は、その後の Todo の完了で少しずつ形になっていく。

その後、ノード集合群（閉路の束）を作るために、延焼（[0004](0004-forest-fire.md)）を入れると決めた。

## 検討した案

### 変異と延焼の両方を MVP に入れる

- どちらも「毎回ちがう形が生まれる驚き」を担っていて、役目が重なる。片方の効果が、もう片方に埋もれる。
- 変異は、MVP には重い機能だった。工数が膨らむ理由は次のとおり。
  - ノード図形集合群の種類ごとに、設計図を別々に実装する必要がある。
  - 設計図を DB に持つので、列が増える（設計図、変異の種類、設計の進み具合、フロントでの未完成の変異の有無）。未完成の変異があるときは、確率的にではあるが、そのノードを優先して育てる。
  - ノードの重なりを防ぐための、当たり判定の処理を実装する必要がある。
- 実装の量も倍になり、MVP が完成しないおそれが一番大きくなる。

### 延焼を外し、変異だけで作る

- 参考画像にある閉路の束を作るには、変異だけでは足りない。

## 決定

変異は MVP に入れない。つまり、ノード図形集合群は MVP では作らない。

## 結果

- 【当初】：決めたときに見込んでいたこと
- 【年-月】：後から分かったこと（分かった時期）

### メリット

- 【当初】設計の複雑なところの多くが変異にあったので、それがまとめて消えた。たとえば、設計図を JSON で持つ方法や、変異したノードを着火点の候補から外す例外の処理である。
- 【当初】延焼のために PlantEdge テーブルが残るので、変異を後から足すときの受け皿は、すでにある。

### デメリット

- 【当初】正八面体のような幾何学的な形（ノード図形集合群）は、MVP では出ない。
