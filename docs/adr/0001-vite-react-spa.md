# 0001. フロントエンドを Vite + React の SPA にする

- 状態：採用
- 決定日：2026-04-07

## 背景

AlGarden は、Todo を完了するたびに庭のノードネットワークが育つアプリで、育つ様子をアニメーションで見せることを体験の中心に置いている。サインインと新規登録の画面を除き、すべての画面はサインインした後に使うもので、検索エンジンに載せるべきページではない。

バックエンドは NestJS で別に作ると決めていた。そのためフロントエンドの役割は、API から受け取ったデータを描き、操作にすばやく反応することだけになる。

## 検討した案

### Next.js

- 一番の強みである SSR / SSG は、SEO 対策が要らない本アプリでは活きない。
- API Routes や Server Actions といったサーバー側の処理を書ける機能を持つため、NestJS と役割が重なる。処理をどちらに書くかを、毎回判断することになる。

## 決定

フロントエンドは、Vite + React の SPA にする。ビルドでできたファイルを配るだけにして、サーバー側の処理は持たせない。

## 結果

【当初】: 決めたときに見込んでいたこと。
【2026-10】: デプロイや見直しで後から分かったこと。

### メリット

- 【当初】サーバー側の処理はすべて NestJS に集まり、どこに書くかで迷わない。
- 【2026-10】web はビルドでできたファイルを配るだけなので、環境変数も関数も要らず、Vercel にそのまま載せられた（#138）。
- 【2026-10】web のサーバーはファイルを返すだけなので、`vercel.json` の rewrites で api に転送するだけで、web と api を同じオリジンに見せられた（#127）。

### デメリット

- 【当初】検索エンジン対策が必要になったら、サーバーで HTML を作れる仕組み（Next.js など）への移行を考える必要がある。
  - 【2026-10】具体的には、庭のシェア機能を作るとき。どの URL を開いても同じ `index.html` が返るため、X や Slack に庭の URL を貼っても、庭ごとのタイトルや画像を出せない。
- 【2026-10】最初に開いたとき、次の3段を順番に待つ。ネットワークのウォーターフォール問題。サインインした後に使うアプリなので、今は受け入れる。
  1. JavaScript の読み込み
  2. `/auth/me` でのサインインの確認
  3. 庭と Todo の取得
