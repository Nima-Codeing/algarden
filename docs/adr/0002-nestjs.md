# 0002. バックエンドを NestJS にする

- 状態：採用
- 決定日：2026-03-25

## 背景

AlGarden は、学習コストの低さを軸にして技術を選んだ。フロントエンドで TypeScript を使うことは決まっていたので、学習コストの観点から、バックエンドも TypeScript で書くと決めていた。API は、シンプルで学習コストが低いことから、REST API にすると決めていた。

NestJS と Express はどちらも使ったことがなかったので、調べた範囲で選んだ。

## 検討した案

### Express

- アーキテクチャの自由度が高く、自分では扱いきれないと感じた。

## 決定

バックエンドは、NestJS にする。

- アーキテクチャがきっちり決まっていて大規模向けではあるが、controller・service・module の決まりがあるので、Todo や Garden などの概念を整理しやすい。置き場所も決まっているので、自分でも扱えそうだと判断した。
- 前に触ったことのある Spring Boot と考え方が似ていて、学習コストが少し下がる。

## 結果

【当初】: 決めたときに見込んでいたこと。
【2026-10】: デプロイや見直しで後から分かったこと。

### メリット

- 【当初】コードの秩序が担保されているため、書き方に迷わない。
- 【2026-10】NestJS は Spring Boot から強く影響を受けているらしい。当時の「Spring Boot に似ている」という感覚は合っていて、学習コストの面では最適だったと思う。
- 【2026-10】MVP を作り終えた時点でも、NestJS のおかげでコードの秩序を守れている。
- 【2026-10】DI で、乱数などの関数をテストで差し替えられた。

### デメリット

- 【2026-10】フロントエンドとの型は、モノレポの共有フォルダで共有している。Hono の RPC を使えば、これをもっとスマートに実装できる。
