# 0002. バックエンドを NestJS にする

- 状態：採用
- 決定日：2026-04-07

## 背景

バックエンドは、学習コストの観点からフロントエンドと同じ TypeScript で書くと決めていた。api には認証・Todo・庭・ノードの成長といった複数の領域があり、それぞれの処理をどこに置くかの決まりが必要だった。Express を使ったことがなく、調べた範囲で比べて決めた。



## 検討した案

### Express

- NestJS の方が TypeScript で書くことが前提となっていて親和性が高い。
- 柔軟に設計できるため、フォルダ構成・設計等に時間を割いてしまう。

## 決定

バックエンドは、NestJS にする。構造がある程度決まった設計で効率的な開発ができる。

## 結果

【当初】: 決めたときに見込んでいたこと。
【2026-10】: デプロイや見直しで後から分かったこと。

### メリット

- 【当初】コントローラー・サービス・DTO の置き場所が決まっているので、領域が増えても同じ形で効率的に書ける。
- 【2026-10】DI によって、汎用関数（乱数生成 etc...）をテストで差し替えられた。
- 【2026-10】Vercel が NestJS を設定なしで動かすことができたので、api を Vercel Functions に載せられた。（[#119](https://github.com/Nima-Codeing/algarden/issues/119)）。


### デメリット

- 【当初】Express より学習コストが高い。
- 【2026-04】class-validator のデコレーターに ESLint が `no-unsafe-call` を出すので、DTO のファイルだけこのルールを切っている。
- 【2026-10】しばらくアクセスがないと、最初のアクセスで NestJS の起動を約1.5秒待つ（Vercel のコールドスタート）。
